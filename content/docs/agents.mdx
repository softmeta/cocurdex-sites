Cocurdex coordinates **multiple agent sessions** in one workspace. Runtimes and providers evolve during pre-release; this page describes the product model and the agents available today.

## Mental model

- Each session has a clear **status** and derived **attention** state (see [Desktop](/docs/desktop/)).
- You can run **more than one** session without merging them into a single transcript.
- Permissions, questions, and plan approvals surface in the UI instead of happening silently.
- Prefer the **narrowest** permission and write mode that still lets the task complete.

## Supported agents

| Id (`--agent`) | UI label | Runtime | Notes |
| --- | --- | --- | --- |
| `claude-agent` | Claude Agent | External `claude` CLI | Plan mode, steering, native write |
| `codex` | Codex | External `codex` CLI | Plan mode, steering, native write; auth via Codex itself |
| `cursor` | Cursor | External `cursor-agent acp` (ACP) | Streaming, native write; no plan mode or steering; login via Cursor |
| `devin` | Devin | External `devin acp` (ACP) | Streaming, native write; no plan mode or steering; login via Devin |
| `grok-build` | Grok Build | External `grok` CLI (ACP) | Plan mode, steering over ACP; native write only |
| `opencode` | OpenCode | External `opencode` CLI | Plan mode, streaming; steering not supported |
| `pi` | Pi | Built-in | Uses your [provider configs](/docs/providers-and-settings/) and [MCP servers](/docs/providers-and-settings/#mcp-servers); read-only write mode |

External agents must be installed and authenticated on your machine. If a CLI is missing, the agent shows as unavailable until you install it — **Settings → Adapters** shows what was detected and how to install the rest.

**ACP** agents (Cursor, Devin, Grok Build) speak the [Agent Client Protocol](https://agentclientprotocol.com). Cocurdex reads their model catalog and session modes from the agent itself, so the choices you see track the installed CLI version.

### Choosing a runtime

| Situation | Start with |
| --- | --- |
| You already use Claude Code / Claude CLI | `claude-agent` |
| You already use OpenAI Codex | `codex` |
| You want Grok-oriented implementation | `grok-build` |
| You use OpenCode elsewhere | `opencode` |
| You have a Cursor subscription | `cursor` |
| You use Devin | `devin` |
| Lightweight chat-style turn without native workspace write | `pi` (Pi) |

## Providers and models

Agents use **provider configs** (API base URL, credentials, catalog) and **models** registered in the app. Configure providers in the desktop UI; list them from the CLI:

```bash
cocurdex provider list
cocurdex provider models <provider-id>
```

Cocurdex reuses your existing provider setup where possible (for example Codex account state under `~/.codex`). Do not paste secrets into product notes or the public docs site.

## Permission modes

Permission modes are **agent-specific**. Risk levels:

| Risk | Intent |
| --- | --- |
| **normal** | Ask or carefully gate tool use |
| **elevated** | Broader auto-approve for edits / review |
| **dangerous** | Full or bypass-style access — use deliberately |

### Claude Agent

| Mode id | Risk |
| --- | --- |
| `claude-default` | normal |
| `claude-accept-edits` | elevated |
| `claude-auto` | elevated — offered when the installed Claude CLI supports auto mode; not available on Haiku models |
| `claude-bypass-permissions` | dangerous |

When the collaboration mode is `plan`, the session uses `claude-plan` (plan only, no edits or commands). Switching back to `default` restores `claude-default`.

### Codex

| Mode id | Risk |
| --- | --- |
| `codex-read-only` | normal |
| `codex-auto` | elevated |
| `codex-full-access` | dangerous |

### Grok Build

| Mode id | Risk |
| --- | --- |
| `grok-ask` | normal |
| `grok-auto` | elevated (Grok’s risk classifier; may cost extra model calls) |
| `grok-always-approve` | dangerous |

### OpenCode

| Mode id | Risk |
| --- | --- |
| `opencode-ask` | normal |
| `opencode-allow` | elevated |
| `opencode-deny` | normal |

### Cursor and Devin

No Cocurdex-side permission-mode list. Tool approval follows the agent's own ACP permission requests, which surface as permission cards like any other agent.

### Built-in Pi (`pi`)

No separate permission-mode list; write mode is **read-only**.

When an agent requests a privileged action, Cocurdex surfaces a permission card (and may show path/action detail). Resolve from the session UI or from `session tui` in the CLI.

## Collaboration and write modes

| Control | Values | Meaning |
| --- | --- | --- |
| **Collaboration** | `default`, `plan` | Plan mode when the runtime supports a plan-first loop |
| **Write mode** | `read-only`, `native-write` | Whether tools may change the workspace |

Not every agent supports every combination. For example, Grok Build focuses on native write; built-in `pi` is read-oriented.

## Agent roles

An **agent role** is a saved preset: agent + provider/model + permission mode + collaboration and reasoning axes, plus optional instructions and skills. Manage roles under **Settings → Roles** (or save the current session's setup as a role from the session UI), and list them from the CLI:

```bash
cocurdex role list
```

Apply a role when you start a session, or give one to a [teammate](/docs/teams/#agent-teams) or a [script-run subagent](/docs/teams/#script-runs).

## Cocurdex agent tools

Every session gets a local MCP tool server from the daemon. Tools are grouped and only offered where they make sense:

| Group | Tools | Offered to |
| --- | --- | --- |
| `team` | `spawn_teammate`, `spawn_template`, `list_roles`, `list_templates`, `stop_member`, `stop` | Main sessions (team leads) |
| `team` | `task_create`, `task_list`, `task_update` | Main sessions and teammates |
| `messaging` | `list_agents`, `send_message` | Main sessions and teammates |
| `script_run` | `propose` | Main sessions |
| `settings` | `list`, `get`, `set`, `propose` | Main sessions (also powers the [settings assistant](/docs/providers-and-settings/#settings-assistant)) |

Subagents started by a script run get none of these tools.

See [Teams and orchestration](/docs/teams/) for what they do.

## In-session controls

Some runtimes can change **model**, **thinking / reasoning effort**, **permission**, or related axes **without recreating** the provider session. That preserves conversation continuity and provider-side cache. If a control is missing for an agent, it is intentionally unsupported — there is no silent “restart the session under the hood” fallback.

## Steering and follow-ups

When an agent supports **steering**, you can send follow-up guidance while a run is active (or queue follow-ups until the current turn finishes — configurable in chat settings). When steering is unavailable, wait for the turn to finish or stop the session.

Stop a running session from the UI or:

```bash
cocurdex session stop <session-id>
```

## Parallel sessions

Typical pattern:

1. One session implementing a feature  
2. One session investigating a bug or reviewing a branch  
3. Optional plan-mode session for design  

Keep titles short and status visible. Switch only when attention demands it — do not merge unrelated work into one transcript to “save a session slot.”
